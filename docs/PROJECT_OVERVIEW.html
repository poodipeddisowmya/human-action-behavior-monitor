01 · What it does

Detect people, keep their identity, understand their actions, log everything.

The system takes a video stream — a file, an uploaded clip, or a live camera — and continuously answers three questions:

  1. Who is in the frame? Each person gets a stable ID (P001, P002, …) that survives short occlusions.
  2. What are they doing right now? A label — standing, walking, drinking, exercising, crawling, etc. — with a confidence value.
  3. What have they done before? A per-person timeline of past actions: start time, end time, duration, confidence.

Answers stream live to the dashboard over WebSocket and persist to a database so any period can be reviewed later. Sources are swappable at runtime — switch between sample clips or upload a new video from the browser without restarting the pipeline.

02 · Pipeline

One detection pass, a branching classification step, then delivery.

Detection and tracking run on the main pipeline thread at the source's native frame rate. Classification branches: a fast pose-based read happens inline; a deep model runs asynchronously on a separate thread and only when the fast read can't identify a specific activity. Neither path blocks the other.

03 · Classification engine

How one action label actually gets decided.

This is the part worth understanding in detail, because it's where accuracy, speed, and honesty all trade off against each other. The system does not run one model and trust its output. It runs two classifiers with very different strengths and lets a composer arbitrate.

Layer 1 — the pose classifier (always on, < 1 ms)

YOLOv8-pose already produces 17 COCO keypoints per person as a side-effect of detection — no extra inference cost. A pure-Python rule engine (src/action_recognition/action_classifier.py) reads those keypoints every frame and can resolve 16 distinct actions from geometry alone:

CategoryActions & the geometric signal used
Motionwalking / running — bounding-box center displacement per second, normalized to body-heights so it works at any distance from camera. falling — a fast downward spike in that same signal.
Posturestanding / sitting / kneeling / lying / bending — ratios between shoulder, hip, knee and ankle heights.
Body-basedpush-up — torso near-horizontal, wrists below shoulder line, ankles level with hips. crawling — flat torso, knees at or below hip level, at least one wrist near the floor.
Hand-baseddrinking — wrist within 0.25 body-heights of the nose. using phone — wrist held near face at eye level. waving — one wrist raised well above the shoulders. clapping — both wrists together at chest height. reading — both hands at chest level with the head tilted down.

When none of these rules fire cleanly, the classifier returns a generic label (standing / walking / running) — an honest fallback, never a guess.

Layer 2 — VideoMAE (async, only when needed)

MCG-NJU/videomae-base-finetuned-kinetics (87M params, HuggingFace Transformers) classifies a rolling 16-frame RGB clip per person into one of Kinetics-400's 400 real-world activities — the only way to recognize context-dependent actions like cooking, dancing, or playing music that no amount of keypoint geometry can reveal.

It only runs when Layer 1 returns a generic label — there is no point spending 150-300ms of CPU time confirming what the pose already knows for certain. It runs on a dedicated background thread with a bounded, drop-oldest job queue, so a slow inference never stalls the video feed.

The composer — who wins

pose (specific) pose (generic) deep model

Why this shape, not "just run the deep model on everything"

Running VideoMAE on every person every frame is the naive approach and it's what the system did originally — see Issue 01 below for what that actually caused. Gating the deep model behind the pose classifier's generic signal cuts inference volume by roughly 70-80% on typical footage (most frames are unambiguous walking or standing) while keeping full deep-model coverage for the activities that need it.

06 · Event lifecycle

How raw per-frame guesses become clean, meaningful log entries.

Raw predictions arrive up to ~15 times a second per person. The temporal stage converts that stream into a small, honest set of discrete events: an event opens when a label first appears, stays open while the smoothed label holds, and closes — writing to the database — the moment the label changes.

PersonLabelDurationConfidence
P001standing3.8s0.88
P001walking3.4s0.83

Why events, not per-frame rows

Storing every prediction would fill the database with ~15 rows/person/second of mostly-redundant data. Storing only change points keeps the log small and directly readable.

07 · Model choices

Why each model, and what didn't make the cut.

Action recognition

ApproachSizeLatencyVerdict
Pose rule engine—< 1 msLayer 1, always on handles 16 common actions from geometry alone.
VideoMAE-base87M / ~350MB150-300 ms CPULayer 2, gated only for context-dependent activities the pose can't see.
ST-GCN (skeleton)~5MB~2 ms/personKept as an optional swap-in — auto-activates if weights are placed in models/, currently unused.
MoViNet-A2 / VideoMAE-large22-350MB+40-120+ msConsidered; VideoMAE-base already covers the label space, and larger models make the CPU latency problem worse, not better.

Design principle

Ship the smallest option that meets the accuracy bar, and gate the expensive model behind a cheap, reliable signal rather than always paying for it. Nothing here is trained from scratch.

08 · Issues & fixes

What actually broke, in the order it broke.

Documented honestly because each of these represents a real design decision, not a typo. Understanding why they happened is the fastest way to understand what the system is actually doing under the hood.

01 Running VideoMAE on every person, every frame, on the pipeline thread fixed
Symptom

Video feed froze/stuttered badly with more than 2-3 people in frame; effective FPS dropped to ~1.

Cause

VideoMAE-base takes 150-300 ms per inference on CPU. Running it inline, synchronously, for every tracked person on every stride meant the whole video pipeline waited on the slowest model call.

Fix

Moved inference to a dedicated background thread with a bounded (max 4), drop-oldest job queue. The pipeline thread submits a clip and immediately continues; the classifier returns the last cached prediction until a new one lands. Also gated invocation behind the pose classifier (Layer 1) so VideoMAE only runs when actually needed — see section 03.

02 Confidence threshold tuned back and forth — too loose vs. too strict fixed
Symptom

At a low bar (0.30) the system surfaced wrong, oddly-specific Kinetics labels ("tossing coin", "waxing legs") on ordinary walking footage. At a high bar with a 2-hit sustain requirement, correct labels took 2+ seconds to appear and mostly never did on short clips.

Cause

Kinetics-400's label space is dense with narrow, easily-confused classes. A single confidence threshold can't simultaneously reject noise and admit true positives when the model is uncertain by nature on out-of-distribution footage.

Fix

Landed on 0.45 with single-hit acceptance (not sustained), plus an explicit noise-label blocklist for classes that are almost never correct on generic surveillance footage (tossing coin, shot put, etc.), plus a mild-override map for oddly-specific-but-plausible classes (waxing legs → grooming). This is a tuned heuristic, not a solved problem — see Current limits.

03 Deep model overriding a correct, specific pose label fixed
Symptom

A person doing push-ups (clear pose signal) would flicker to a VideoMAE-guessed unrelated label mid-clip.

Cause

Early versions let any fresh deep prediction override the current label regardless of what the pose classifier had already determined.

Fix

Composer rule: a specific pose label (drinking, push-up, crawling, sitting, etc.) always wins outright and VideoMAE isn't even invoked. The deep model only gets a vote when the pose classifier itself is uncertain (generic standing/walking/running).

04 Per-crop MediaPipe pose degraded badly on distant people fixed
Symptom

On surveillance-angle footage (people small in frame), pose keypoints were unreliable or missing entirely.

Cause

The original design cropped each detected person and ran MediaPipe Pose on the crop. MediaPipe assumes the person roughly fills the input frame; a small, low-resolution crop from a wide shot violates that assumption.

Fix

Switched to YOLOv8-pose, which estimates pose on the whole frame in the same pass as detection — giving it full scene context and making it far more robust to scale. This also removed an entire per-person crop + inference step, improving speed.

05 Crawling misclassified as "standing" (reported by user, real footage) fixed
Symptom

A baby clearly on all fours, fully horizontal, labeled "standing" in the live feed.

Cause

The crawling rule required the torso-tilt ratio to fall strictly between 0.05 and 0.28 body-heights. A body that is fully horizontal (baby on all fours) has a tilt ratio near 0.02 — just under that lower bound — so the rule silently failed to fire and the classifier fell through to the generic motion label. The rule's check order also ran after the "lying" check, so ambiguous horizontal poses could get claimed by the wrong rule first.

Fix

Removed the lower bound (crawling now accepts any flat torso < 0.32, no floor), and reordered checks so crawling and push-up are evaluated before lying — both are horizontal-torso states, but crawling/push-up have hands+knees engaged with the floor while lying is a static, fully-supine pose.

Pattern across these issues

Every fix here came from testing against real, varied footage rather than trusting the model cards. Public benchmark datasets (HMDB51 previews especially) are short, low-resolution, and don't exercise pose geometry the way real client footage does — several of these bugs were invisible until footage of an actual person was uploaded.

09 · Current limits

What's still honestly a limitation, and what closes it.

LimitationWhyWhat closes it
VideoMAE inference is slow on CPU (150-300 ms) 87M-parameter transformer with no hardware acceleration. GPU deployment (~15 ms/inference, 10× faster) — no code change, the pipeline already checks settings.device.
Kinetics-400 labels don't always match a specific deployment's scenes The deep model was trained on YouTube-style clips, not the client's exact environment (camera angle, lighting, clothing, room layout). Fine-tuning on ~200-300 labeled clips per action from the client's own footage — a few days of work, not a config change.
Hand-based pose rules (drink / phone / wave / clap / read) need visible wrists Heavily occluded arms, low resolution, or motion blur drop keypoint confidence below the visibility floor. Higher-resolution source video and closer camera framing; alternatively a hand-specific detector as a third layer.
Confidence thresholds are hand-tuned heuristics No labeled validation set exists yet to calibrate them statistically. Build a small labeled evaluation set from client footage and calibrate thresholds against precision/recall targets (the src/evaluation module already has the scaffolding).

11 · UI dashboard

What the operator actually sees.

  • Live feed. Annotated MJPEG stream with coloured boxes, ID, current label, confidence.
  • Source selector. Dropdown to switch clips mid-demo + an upload button for any local video (up to 500MB).
  • People. Every tracked ID with search. Click to open the detail panel.
  • Person detail. Current action, confidence, first/last seen, full activity timeline.
  • Recent events. Live-updating table across all people, colour-coded for safety-critical labels.

Every panel updates via WebSocket — no refresh button, no polling.

12 · Running it

cd Human-Action-Behavior-Monitor
